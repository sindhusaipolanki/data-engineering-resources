# Daily Data Engineering Tips — November 2026


## 2026-11-01 — Delta Lake: Time travel for safe backfills

Before a risky backfill, note the current Delta version with `DESCRIBE HISTORY`. If the backfill goes wrong, restore with `RESTORE TABLE ... TO VERSION AS OF N` — no need for a backup restore.

```sql
-- Check current version before backfill
DESCRIBE HISTORY delta.`/mnt/gold/fact_sales`;

-- Restore if something goes wrong
RESTORE TABLE delta.`/mnt/gold/fact_sales` TO VERSION AS OF 42;
```

## 2026-11-02 — PySpark: Avoid Python UDFs — use native Spark functions

Python UDFs serialize data to Python, process row-by-row, and serialize back. Native Spark functions (`pyspark.sql.functions`) run in the JVM and can be 10–100x faster. Use `pandas_udf` when you truly need Python logic.

```python
# Bad — Python UDF (slow)
@udf(StringType())
def upper(s): return s.upper() if s else None

# Good — native function (fast)
from pyspark.sql.functions import upper
df.withColumn('name', upper(col('name')))
```

## 2026-11-03 — SQL: CTEs improve readability and performance

Common Table Expressions (CTEs) make complex queries readable and allow the optimizer to reuse subquery results. In most modern engines, a CTE referenced once is inlined; referenced twice, it may be materialized.

```sql
WITH monthly_sales AS (
  SELECT DATE_TRUNC('month', sale_date) AS month,
         SUM(amount) AS total
  FROM sales
  GROUP BY 1
),
ranked AS (
  SELECT *, RANK() OVER (ORDER BY total DESC) AS rnk
  FROM monthly_sales
)
SELECT * FROM ranked WHERE rnk <= 3;
```

## 2026-11-05 — PySpark: Cache DataFrames used more than twice

If you read the same DataFrame in 3+ actions (count, write, join), call `.cache()` after first creation. Spark recomputes lineage from scratch on every action otherwise. Unpersist when done to free memory.

```python
silver_df = transform(bronze_df).cache()

row_count = silver_df.count()          # action 1 — reads from cache
silver_df.write.delta.save(path)       # action 2 — reads from cache
silver_df.join(dim_df, 'id').show()    # action 3 — reads from cache

silver_df.unpersist()
```

## 2026-11-07 — SQL: Lateral joins replace correlated subqueries

Correlated subqueries run once per row — they're O(n²). Replace them with LATERAL (or CROSS APPLY in SQL Server) to evaluate once and join the result set efficiently.

```sql
-- Correlated subquery (slow)
SELECT c.customer_id,
  (SELECT MAX(sale_date) FROM sales s WHERE s.customer_id = c.customer_id) AS last_purchase
FROM customers c;

-- LATERAL join (fast)
SELECT c.customer_id, s.last_purchase
FROM customers c
LEFT JOIN LATERAL (
  SELECT MAX(sale_date) AS last_purchase FROM sales WHERE customer_id = c.customer_id
) s ON true;
```

## 2026-11-09 — PySpark: Broadcast small dimension tables

For dimensions under ~100MB, broadcast them to all executors to avoid a shuffle join. Spark may auto-broadcast based on `spark.sql.autoBroadcastJoinThreshold`, but explicit hints are more reliable.

```python
from pyspark.sql.functions import broadcast

# Explicit broadcast hint
result = fact_df.join(
    broadcast(dim_product),
    'product_id'
)
```

## 2026-11-10 — Delta Lake: Schema enforcement protects your pipeline

Delta Lake enforces schema by default — writes with unexpected columns fail loudly. Use `mergeSchema=true` only at Bronze where sources evolve. Silver and Gold should fail on schema mismatches so you catch upstream changes early.

```python
# Bronze — allow schema evolution
bronze_df.write.format('delta')\
  .option('mergeSchema', 'true')\
  .mode('append').save(bronze_path)

# Silver — enforce strictly (default, no option needed)
silver_df.write.format('delta').mode('append').save(silver_path)
```

## 2026-11-11 — SQL: Use EXPLAIN ANALYZE before optimizing

Never guess at performance bottlenecks — run EXPLAIN ANALYZE to see the actual execution plan and row estimates. Look for seq scans on large tables, bad row estimates, and nested loop joins on large datasets.

```sql
-- PostgreSQL / Synapse
EXPLAIN ANALYZE
SELECT c.customer_name, SUM(s.amount)
FROM sales s
JOIN customers c ON s.customer_id = c.customer_id
WHERE s.sale_date >= '2024-01-01'
GROUP BY c.customer_name;
```

## 2026-11-12 — Data Quality: Row count checks catch silent failures

Always assert row count > 0 after every pipeline stage. Silent empty DataFrames that pass through to Gold corrupt downstream reports with no error message. A simple count check costs milliseconds.

```python
def assert_not_empty(df, stage: str) -> None:
    count = df.count()
    if count == 0:
        raise ValueError(f'{stage} produced 0 rows — check upstream source')
    print(f'{stage}: {count:,} rows OK')
```

## 2026-11-13 — Microsoft Fabric: Partition your Lakehouse tables by date

## 2026-11-14 — PySpark: Use monotonically_increasing_id for surrogate keys

Need a unique ID for every row in a large DataFrame? `monotonically_increasing_id()` generates unique 64-bit integers without a shuffle — unlike `row_number()` which requires sorting across partitions.

```python
from pyspark.sql.functions import monotonically_increasing_id

df_with_id = df.withColumn('surrogate_key', monotonically_increasing_id())
```

## 2026-11-15 — SQL: Avoid SELECT * in production queries

SELECT * reads all columns — even ones you don't need. On columnar formats (Parquet, Delta), this defeats column pruning and reads 3–10x more data than necessary. Always name your columns explicitly.

```sql
-- Bad — reads all columns from Parquet
SELECT * FROM gold.fact_sales WHERE year = 2024;

-- Good — only reads 4 columns from disk
SELECT sale_id, customer_id, amount, transaction_date
FROM gold.fact_sales
WHERE year = 2024;
```

## 2026-11-16 — Azure Data Factory: Use variables for dynamic pipeline dates

Hardcoding dates in ADF queries breaks on re-runs and backfills. Use pipeline parameters + system variables like `@utcNow()` and `@formatDateTime()` so pipelines work for any run date.

## 2026-11-17 — Delta Lake: Use MERGE for idempotent upserts

MERGE (Delta's upsert operation) is idempotent — safe to re-run if a job fails. It updates existing records and inserts new ones in a single atomic operation, replacing the delete-then-insert anti-pattern.

```python
DeltaTable.forPath(spark, target_path)\
  .alias('t')\
  .merge(source_df.alias('s'), 't.id = s.id')\
  .whenMatchedUpdateAll()\
  .whenNotMatchedInsertAll()\
  .execute()
```

## 2026-11-18 — Data Quality: Track null rates per column at Silver layer

Compute null rate for every column at Silver ingestion. Set a threshold (e.g., >5% = fail). Null spikes indicate upstream schema changes or source system issues — catch them before they reach Gold.

```python
def null_rates(df) -> dict:
    total = df.count()
    return {
        col: df.filter(F.col(col).isNull()).count() / total
        for col in df.columns
    }
```

## 2026-11-19 — PySpark: Repartition before writing to avoid small files

Spark writes one file per partition. If your DataFrame has 200 partitions but only 1M rows, you get 200 tiny files — the small file problem. Coalesce or repartition before writing.

```python
# Target ~128MB per file
# For 10GB of data → 80 partitions
df.coalesce(80)\
  .write.format('delta')\
  .mode('append')\
  .save(output_path)
```

## 2026-11-20 — SQL: Index foreign key columns in fact tables

Fact tables join to dimensions on foreign keys. Without indexes on those columns, every join does a full table scan. Add non-clustered indexes on all FK columns in your fact tables.

```sql
-- SQL Server / Azure SQL
CREATE NONCLUSTERED INDEX IX_fact_sales_customer
  ON dbo.fact_sales (customer_id)
  INCLUDE (amount, transaction_date);

CREATE NONCLUSTERED INDEX IX_fact_sales_product
  ON dbo.fact_sales (product_id)
  INCLUDE (amount, quantity);
```

## 2026-11-22 — Data Quality: Use Great Expectations for automated data contracts

Define data expectations as code — column types, value ranges, referential integrity. Run them in your pipeline as a quality gate. Failed expectations block the write and alert the team before bad data reaches consumers.

```python
import great_expectations as gx

context = gx.get_context()
suite = context.add_expectation_suite('silver.sales')
suite.add_expectation(
    gx.expectations.ExpectColumnValuesToBeBetween(
        column='amount', min_value=0, max_value=1_000_000
    )
)
```
